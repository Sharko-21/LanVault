## Что изменилось

- Полная библиотека и ручной выбор передаются двумя задачами. Сервер уже имеет два слота приёма; очередь ограничена текущей страницей MediaStore. Счётчики и callbacks сериализованы, обе задачи завершаются при отмене или ошибке. Полная синхронизация показывает оба активных файла.
- Обновления байтового прогресса ограничены 10 разами в секунду на файл; смена стадии и завершение показываются сразу. Запись на ПК буферизована по 256 КиБ с учётом ещё не сброшенного буфера при проверке свободного места. Flush, sync, проверка SHA-256, публикация без перезаписи и долговечная квитанция сохранены.
- Квитанция COMMITTED не заменяется состоянием INTERRUPTED, если интерфейс остановился после её сохранения.
- При запуске восстанавливаются только незавершённые `committing`-операции. Ранее весь архив повторно хешировался и проводился через две FULL-sync транзакции на файл. Для завершённых копий запуск проверяет существование и размер, а полный хеш проверяется перед выдачей существующей квитанции и при фиксации нового оригинала. Повреждение с сохранением размера обнаруживается при таком запросе, а не быстрым стартовым аудитом. Отсутствующий файл не получает ложный успех и восстанавливается в новом безопасном назначении.
- Desktop записывает безопасные коды ошибок инициализации и автоматического восстановления в stderr.

Обновлённый Desktop собран и запущен: `192.168.1.68:43827`, физический Ethernet. Сохранены 3053 здоровые квитанции, 3047 различных файлов и три действующих записи доверия; каталог `D:\Sync`. Указанные числа — снимок после перезапуска. Ярлык рабочего стола продолжает ссылаться на тот же EXE. Управление окнами прекращено после пользовательского Esc; итоговый порт проверен через Windows TCP API.

## ASTER: причина и готовое исправление

Действующее дерево: `<aster-source>`. В режиме сайтов ASTER разрешал прямые сокеты только своему прокси, а обычный LanVault попадал под жёсткую блокировку WFP. Вариант IP-exclude нельзя смешивать с текущими доменными правилами. Прямой маршрут Ethernet уже существовал; смена метрики и обычное правило Windows Firewall не исправляют фильтр ASTER.

В три исходных файла ASTER внесено независимое, включаемое администратором разрешение локального TCP-сервиса. Оно связывает точный AppID EXE, локальный IPv4, порт, удалённую частную подсеть и LUID действующего аппаратного Ethernet/Wi-Fi. Публичные адреса, DNS, IPv6 и остальные приложения этим исключением не разрешаются. Временные защитные фильтры обновления и восстановления остаются строгими. Маршруты и доменные списки не меняются. mDNS этим TCP-исключением не открыт; Android использует сохранённый адрес и ограниченный прямой TCP-поиск.

Подготовлен кандидат `artifacts/aster-lan/package`, его хеши, регистрация `192.168.1.68:43827` для `192.168.1.0/24` и скрипт `tooling/install-aster-lan.ps1`. Кандидат установлен 04.11.2026; итог приведён в последнем разделе. Скрипт требует Windows Administrator, проверяет хеши и физическую частную сеть, использует уже установленный ASTER для подписи кандидата существующим защищённым DPAPI-ключом и выполняет штатный signed update. Ключ не экспортируется. Если ключ недоступен или подпись не совпадает с якорем установки, обновление отклоняется. Регистрация других сервисов сохраняется; при неудаче восстанавливается прежний конфиг.

Команда установки (уже выполнена от имени администратора 04.11.2026):

```powershell
& 'lanvault\tooling\install-aster-lan.ps1'
```

После успешного обновления оставьте оба VPN включёнными и запустите синхронизацию в новом APK. Повторный QR не требуется. Реальная передача Pixel с этой установкой ещё не проверена; изолированный административный WFP-тест и проверка установленного фильтра пройдены. Регистрация привязана к текущему локальному IP и порту; при их изменении её потребуется обновить. Не запускайте неподписанный кандидат напрямую вместо установленного клиента.

## Исправление AppID и проверка реальной передачи — 04.11.2026, 22:27 МСК

При воспроизведении `TCP_CONNECTION_TIMEOUT` пассивный сбор WFP показал блокировку `192.168.1.64:49804 → 192.168.1.68:43827` правилом `ASTER: fail-closed default` на слое входящего accept. В разрешающем правиле оставались заглавные буквы в `Документы\Хранилище`, а AppID ядра содержал `документы\хранилище`. Строки не совпадали побайтово; после Unicode lowercase совпадали полностью. Согласно [документации Microsoft для ALE_APP_ID](https://learn.microsoft.com/en-us/windows/win32/fwp/filtering-condition-identifiers-), идентификатор представляет собой device path в нижнем регистре.

В `localServiceRules` добавлена нормализация Unicode AppID до установки byte-blob условия. Сохраняются все шесть ограничений, только входящий TCP accept; новые исходящие соединения и прямой DNS по-прежнему запрещены. Добавлены тест по фактическому AppID события и тест настоящего `wf.AppID` для EXE в каталоге с кириллицей. Оба сначала воспроизвели дефект старого кода, затем прошли с исправлением.

Полный запуск `GODEBUG=http2xconnect=1 go test -tags=http2legacy ./... -count=1` дал **267 passed, 7 opt-in skipped, 0 failed**; `go vet -tags=http2legacy ./...` прошёл. Первоначальные запуски без обязательного окружения/тега HTTP/2 завершались ошибками конфигурации интеграционных тестов; их логи сохранены отдельно. Собран и штатно подписан/установлен **0.13.3-experimental**, sequence 42, SHA-256 `E15896A7FFD13748F6BE2A5A94415B28F3405C850E15C942F6FCDEC240D3DAED`.

Установленное правило теперь точно совпадает с AppID из реального события ядра. VPN подключён по H3, `routing.json` не изменён, постоянная политика PowerShell остаётся Restricted. Пользователь подтвердил начало передачи с включённым ASTER; на ПК наблюдалось установленное соединение с `192.168.1.64` и рост квитанций с 3087 до 3107.
