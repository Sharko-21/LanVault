# Этап 3 — Desktop MVP

Реализован рабочий Windows-приёмник с локальным управлением через Desktop. Проверки выполнены 4 ноября 2026 на текущей Windows-машине. Android и автоматическая синхронизация остаются следующими этапами.

## Результат

- Настоящий TLS 1.2/1.3 сервер, выбранный частный физический IPv4-интерфейс, фильтр подсети, ограничение ресурсов и остановка при изменении сети. По умолчанию после запуска приём выключен.
- Одноразовый QR, 120 секунд, сравнение кодов и явное локальное подтверждение. Для каждого телефона отдельный случайный токен; отзыв останавливает его активные передачи и сохраняет готовые копии. Административных HTTP-маршрутов нет.
- Системный выбор папки, сохранённый dataset, свободное место и резерв. Новый каталог создаёт отдельный архив, прежние копии остаются на месте.
- Потоковая запись исходных байтов в `.lanvault/staging`, полный SHA-256, sync, журнал `committing`, публикация без перезаписи и устойчивое подтверждение SQLite WAL/FULL. Повторные запросы и восстановление до/после rename проверяются реальными файлами.
- Защита от traversal, ADS, hard link, junction/reparse и подмены предков. Создание и rename относительно живых NT-дескрипторов. Канонический путь получается по дескриптору; имя клиента не задаёт путь назначения.
- CA и временная выдача credentials защищены DPAPI; отдельный каталог состояния имеет DACL текущего пользователя и SYSTEM. В основной таблице устройств только хеш токена. Диагностические ошибки ядра не раскрывают секретов, имён и абсолютных путей.
- Трей: открыть окно, пауза/продолжить, остановить приём, выйти. Закрытие окна скрывает его; выход дожидается остановки listener. UI показывает реальные устройства, прогресс, копии и историю, поддерживает темы.

Минимальная серверная часть сопряжения и проверки целостности появилась уже здесь, поскольку безопасный приёмник требует авторизации и подтверждения сохранения. Discovery, Android-клиент, устойчивые части и фоновые задания по-прежнему относятся к своим этапам. Решение зафиксировано в [ADR-0013](../adr/0013-desktop-mvp.md).

Отдельные тесты подтверждают WAL, synchronous FULL, foreign keys, integrity_check, отказ от неизвестной новой схемы до миграции, точное Unicode-имя после rename, запрет перезаписи, блокировку переименования предка, отказ hard link/ADS и DPAPI с обнаружением изменения шифротекста.

HTTPS-набор использует проверенный CA и hostname, не отключает TLS-проверку. Создаёт только синтетические файлы во временных папках и убирает собственные процессы/файлы. Сценарии:

1. Сопряжение требует локального подтверждения; повторная выдача credentials идемпотентна.
2. Недоверенный CA отвергается.
3. Неверный hostname отвергается.
4. Обычный HTTP не принимается TLS-listener.
5. Отсутствующий/поддельный токен отвергается.
6. Запрос с browser Origin отвергается.
7. Исходные непрозрачные байты с EXIF-подобной нагрузкой сохраняются без изменений и проверяются SHA-256.
8. Повтор request UUID возвращает тот же receipt; конфликт метаданных — 409.
9. Дедупликация не передаёт байты повторно и правильно связывает новый media/revision receipt.
10. Traversal в имени не выходит из архива и не меняет внешний sentinel.
11. Неверный SHA-256 не даёт успешного receipt.
12. Пауза блокирует новую передачу.
13. Видео 64 МиБ передаётся потоком с ограниченным буфером клиента.
14. Обрыв тела и принудительное завершение процесса допускают повтор с нуля.
15. Журнал восстанавливает commit до и после rename. Оба окна воспроизведены детерминированно через состояние БД/диска при остановленном процессе.
16. Второе доверенное устройство не читает чужую загрузку.
17. Внешнее удаление готового файла исключает повторный успешный receipt.
18. Перезапуск без передачи пути архива сохраняет CA, токен, выбранную папку и подтверждения.
19. Отзыв отвергает токен, оставляя сохранённые байты.
20. SQLite integrity_check и хранение хеша токена.
21. Невыполнимый резерв места даёт 507 до приёма байтов.
22. NTFS junction отклоняется до запуска listener.
23. OneDrive-корень отклоняется и после нормализации длинного Windows-пути.

Локальные журналы находятся в игнорируемом `artifacts`: `web-check.log`, `desktop-check.log`, `native-tests.log`, `server-integration.log`, `clippy.log`, `desktop-build.log`, `project-validation.log`, `desktop-runtime.log`. Наличие workflow не считается прохождением GitHub CI: удалённый CI в этой работе не запускался.

## Запуск

Окончательная сборка Desktop уже открыта. Для повторного запуска на **этой машине** из `lanvault`:

```powershell
$env:LANVAULT_DEV_STATE_DIR = Join-Path $env:TEMP 'LanVault-Desktop-MVP-state'
& .\target\gnu\debug\lanvault-desktop.exe
```

Рядом должен оставаться `WebView2Loader.dll`. Управляемая среда перенаправляет AppData, и no-reparse защита отвергает такой путь. Поэтому здесь задан явный каталог состояния в TEMP. Это исключение существует только в debug-сборке; Release использует обычный `%LOCALAPPDATA%/app.lanvault.desktop/server`. DPAPI и файловая защита остаются включены. Временный каталог не подходит для постоянного хранения доверия после очистки TEMP; для эксплуатации нужна обычная установка и проверка на целевом ПК.

Выберите обычную существующую папку NTFS вне OneDrive. Если появится разрешённая частная физическая сеть, выберите её и включите приём; порт 43827/TCP привязывается к одному IPv4. Затем создайте QR и подтвердите совпадающие коды. Приложение не меняет профиль Windows и брандмауэр. Текущий Android ещё не передаёт файлы: до этапа 4 используется тестовый HTTPS-клиент.

Повторить проверки:

```powershell
pnpm check
.\tooling\check.ps1 -Target Desktop -PortableRust
python tooling/validate-project.py
```

Стандартная MSVC-сборка, зависимости и обычный путь запуска описаны в [инструкции разработчика](../installation/development.md). [Рабочий API](../protocol/api.md), [OpenAPI](../protocol/openapi.json).

## Границы результата

- На этой машине проверен Windows GNU debug, Rust 1.94.0 + LLVM-MinGW 20261020 MSVCRT. Системные MSVC/Windows SDK отсутствуют; release MSVC, установщик и подпись ещё не проверены. Инструменты загружались локально в `.tools`, без системной установки.
- Реального Android-телефона, сканирования QR камерой, двух физических устройств LAN и роутера без WAN в испытаниях не было. Для сети проверены политика, реальный запрос Windows и loopback TLS; смена профиля на физическом интерфейсе не воспроизводилась.
- Открытие GUI и системного диалога наблюдалось. Завершение пользовательского выбора папки, меню трея, hide/restore/quit и Windows 10 требуют отдельной интерактивной приёмки; они не выдаются за пройденный GUI E2E-тест. Сохранение/восстановление папки проверено через то же ядро в headless HTTPS-наборе.
- Максимальный тестовый файл — 64 МиБ. Файл больше 4 ГиБ, реальное заполнение диска, физическое отключение питания/USB и высокая нагрузка — будущая матрица. 507 проверяется резервом, а не заполнением пользовательского диска.
- `resumable:false`: повтор всей передачи, без PATCH/chunk offset. Неуспешные `.part` сохраняются для повторной отправки; автоматического TTL-сбора временных файлов пока нет. Готовые копии не удаляются.
- При старте выполняется полная проверка зарегистрированных копий; для большой библиотеки её производительность предстоит оптимизировать.
- Нет mDNS/NSD объявления, автоматического резервирования, autorun, ротации токенов и переноса архива. Смена папки создаёт отдельный dataset, прошлые файлы остаются на диске.
